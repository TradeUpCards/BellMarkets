1. The conceptual model — one book, two tokens

Every strike has one on-chain order book — a Phoenix v1 CLOB market with base = YES token and quote = USDC. The NO token is not a separate book; its price is implicit in the YES price:

Pricing identity

Price(NO) = $1 − Price(YES)  — because at settle, one of them pays $1 and the other pays $0. A user holding 1 YES + 1 NO holds exactly $1 of claim, regardless of outcome.

┌──────────────────────────────────────────────────────────────────────┐ │ StrikeMarket PDA (BellMarkets program) │ │ │ │ ┌─────────────┐ ┌─────────────┐ ┌────────────────────────┐ │ │ │ YES mint │ │ NO mint │ │ USDC vault │ │ │ │ (SPL) │ │ (SPL) │ │ (SPL token account) │ │ │ │ │ │ │ │ authority = StrikeMkt │ │ │ └─────────────┘ └─────────────┘ └────────────────────────┘ │ │ │ │ │ │ └───────────┼─────────────────┼───────────────────────┼────────────────┘ │ │ │ └─────┬───────────┘ │ │ │ ▼ │ ┌──────────────────────────┐ │ │ Phoenix YES/USDC │ ◄──── 1 order │ │ market (single book) │ book per │ │ base = YES │ strike │ │ quote = USDC │ │ └──────────────────────────┘ │ │ At settle, vault pays $1 to each winning token. │ Holding 1 YES + 1 NO ≡ holding $1 of claim. ──────────┘

Invariant: for every strike, vault USDC balance ≥ outstanding_pairs × $1. This is enforced by the program — every mint_pair deposits $1 to the vault; every redeem_pair burns 1 YES + 1 NO and withdraws $1; every redeem (post-settle) burns 1 winning token and withdraws $1.

2. Mint & redeem primitives (where USDC enters & exits)

Phoenix doesn't know how to create tokens out of thin air. The BellMarkets program does. Two primitive instructions handle the conservation of USDC ↔ tokens:

mint_pair — USDC enters the system

1User signs tx with amount (number of pairs to mint).
2Program transfers amount × $1 USDC from user_usdc → usdc_vault.
3Program transfers amount × $0.02 USDC from user_usdc → fee_collector_usdc (the 2% DR-008 mint-only fee).
4Program mints amount YES tokens to user_yes_token.
5Program mints amount NO tokens to user_no_token.
6Program increments strike_market.pairs_outstanding by amount.
After: user paid $1.02, holds 1 YES + 1 NO; vault gained $1; fee collector gained $0.02.

redeem_pair — USDC exits the system (pre-settle close)

1User signs tx with amount (number of pairs to burn).
2Program burns amount YES tokens from user_yes_token.
3Program burns amount NO tokens from user_no_token.
4Program transfers amount × $1 USDC from usdc_vault → user_usdc.
5Program decrements strike_market.pairs_outstanding by amount.
After: user paid 1 YES + 1 NO, got $1 USDC back. No fee on the exit (DR-008 — mint-only).

redeem — USDC exits the system (post-settle win)

1Market is settled; strike_market.outcome ∈ {Yes, No}.
2User signs tx with amount (number of winning tokens to redeem).
3Program enforces winning_mint == strike_market.{yes|no}_mint based on outcome.
4Program burns amount winning tokens from user_winning_token.
5Program transfers amount × $1 USDC from usdc_vault → user_usdc.
After: user paid winning tokens, got $1 per token back. Losing tokens are not redeemable — they're worth $0.

3. The 4 trade combinations — when each is used & how they work

Every action a trader can take maps to exactly one of these four flows. The first two go straight to Phoenix. The last two bundle Phoenix with a BellMarkets mint/redeem primitive — but the user signs ONE transaction (POV-3 atomicity).

BUYYES

"I think the strike resolves YES. I want to bet on it."

Single ix: Phoenix place_order on YES book (buy side)

USDC flows from user → Phoenix maker. YES tokens flow from maker → user.

Worked example Best ask = $0.55. User wants 100 YES.
→ Pays $55 USDC, receives 100 YES.
→ If YES wins at settle: redeem 100 YES for $100 (gain $45).
→ If NO wins: 100 YES worth $0 (loss $55).

SELLYES

"I want to exit my YES position before settle."

Single ix: Phoenix place_order on YES book (sell side)

YES tokens flow from user → Phoenix taker. USDC flows from taker → user.

Worked example User holds 100 YES bought at $0.55. Best bid = $0.62.
→ Sells 100 YES, receives $62 USDC.
→ Realized gain: $7 (locked in pre-settle).

BUYNO

"I think the strike resolves NO. I want to bet against it."

Bundled atomic ix:
  1. BellMarkets mint_pair(amount) — pay $1×amount, get amount YES + amount NO
  2. Phoenix sell amount YES at best bid

User never sees an intermediate YES balance — both ixs land atomically. Net: user paid $1 − bid + fee for each NO.

Worked example Best YES bid = $0.45. User wants 100 NO.
→ mint_pair(100): pays $100 USDC + $2 fee → gets 100 YES + 100 NO
→ sell 100 YES at $0.45 → receives $45 USDC
→ Net: paid $57, holds 100 NO (effective NO price ≈ $0.57)
→ If NO wins: redeem 100 NO for $100 (gain $43).

SELLNO

"I want to exit my NO position before settle."

Bundled atomic ix:
  1. Phoenix buy amount YES at best ask
  2. BellMarkets redeem_pair(amount) — burn amount YES + amount NO, get $1×amount

User never sees intermediate YES — atomic. Net: user paid ask on YES, got $1 back per pair burned. Effective NO sale price ≈ $1 − ask.

Worked example User holds 100 NO bought at $0.57. Best YES ask = $0.40.
→ buy 100 YES at $0.40 → pays $40 USDC, receives 100 YES
→ redeem_pair(100) → burns 100 YES + 100 NO → receives $100 USDC
→ Net: paid $40, got $100 back, no longer holds NO
→ Realized for 100 NO: $60 USDC (vs $57 paid = $3 gain).
POV-3 atomicity

Buy-NO and Sell-NO are one transaction, one signature. If any leg fails, the whole thing reverts — no orphan YES or NO sitting in the user's wallet. See build-buy-no.ts + build-sell-no.ts in the frontend.

When each combination is selectable in the UI

ActionSelectable when…Fails when…
Buy YESAlways — uses Phoenix book directly. Limit always works (posts a bid).Market: no asks on book. Limit: order rests.
Sell YESUser holds ≥ amount YES tokens.No bids on book (market); limit rests.
Buy NOAlways — atomically mints pair + sells YES. Market: needs bids on YES book. Limit: rests as YES sell.No YES bids ≥ user's reservation price.
Sell NOUser holds ≥ amount NO tokens.No YES asks ≤ user's reservation price.

Hard YES #8 (position exclusivity): if user holds NO and tries to Buy YES, UI must require them to close NO first. Same the other way. This prevents accidentally accumulating 1 YES + 1 NO positions that always net to $0 (minus fees).

4. Bootstrapping a market without a market maker

This is the real question Cory asked. The answer is nuanced — there is no atomic complementary-mint on fill in our v1, so the first trader is in an awkward spot:

The first-trader problem

An empty YES order book has no bids and no asks. The first trader who wants to "Buy YES at $0.55" can:

  • Post a limit Buy YES at $0.55 — rests on the book. No fill happens until someone else shows up to sell.
  • OR call mint_pair directly — pays $1, gets 1 YES + 1 NO, then sells the side they don't want via a limit order. Same waiting problem on the sell.

User A's order rests on book. No fill yet. YES order book Vault User A User B ───────────────── ───── ────── ────── ASKS: (empty) $0 $100 $0 ───── (no last) 0 YES (waiting) BIDS: $0.55 × 100 ← User A's bid 0 NO Time T2 — User B wants to bet NO. Notice: the first trade requires two opposite-direction users (one bullish, one bearish) to coincidentally show up. The market doesn't price itself. In practice, market makers (Drift, Polymarket) seed every strike with bid-ask quotes so users always have something to trade against. BellMarkets v1 ships without an MM — initial liquidity depends on user discovery and limit-order patience.

v1 trade-off (Hard YES discussed in DR-008)

For demo: we either (a) seed a few markets manually using mint_pair + limit orders to make them tradeable on-camera, or (b) demo the Buy-YES mint_pair path (which always works because it doesn't need a counterparty — the vault is the counterparty). Our v8 frontend defaults to Buy-YES as the "always works" demo path.

5. Order lifecycle on Phoenix (place / fill / cancel)

Phoenix v1 is a FIFO matching engine. Orders are price-time-priority. The market account stores the full order book on-chain.

Place a limit order

1User signs place_order(price, size, side) tx.
2Phoenix moves price × size USDC (for a bid) or size YES (for an ask) from user's ATA into the Phoenix market's seat account as collateral.
3If the order crosses the opposite side: immediate fill at the resting order's price (price-time priority). User receives the asset; resting maker receives the collateral.
4If the order does NOT cross: it rests on the book as a maker order. Collateral stays in the Phoenix seat.
No fees, no Bell Markets-side state change. All state lives in Phoenix's market account.

Cancel a resting order

1User signs cancel_order tx.
2Phoenix removes the order from the book and returns the collateral to the user's ATA.
No fee was taken when the order was placed → nothing to refund. Clean exit.

Market order (immediate fill, no resting)

1User signs an IOC (immediate-or-cancel) order at the worst-acceptable price (slippage cap).
2Phoenix walks the book, filling as much as it can up to the slippage cap. Unfilled remainder is cancelled (returned to user).
3User receives whatever filled; any unfilled portion is returned immediately.
If the book is too thin and no fills happen: tx succeeds (technically) but user got 0 tokens. UI should warn about thin books before submission. Buy-NO with empty book fails the same way (the YES sell leg has no bids to take).

6. Fees — when, where, and what happens on cancel

This is the part Cory specifically asked about, and the answer is the cleanest piece of our design:

Action Fee charged? When taken Refundable?
mint_pair 2% mint fee Inside the same tx as the USDC deposit (atomic with the mint) No — but mint isn't cancelable. If you don't want the tokens, you'd redeem_pair them back for $1, eating the 2¢ fee.
redeem_pair none — —
redeem (post-settle win) none — —
Phoenix place / fill / cancel none (v1) — (DR-009 Model D would add ~5 bps at fill, v1.5) —
Why cancel is clean — but only because of a deliberate v1 design choice

Phoenix doesn't charge a placement fee. BellMarkets only takes the 2% fee inside mint_pair. So cancelling a Buy YES or Sell YES order requires no refund — no money left the user, Phoenix just returns the collateral.

For Buy NO / Sell NO, we have a stricter rule: v1 ships these as market-only (IOC swaps). If the Phoenix leg can't fill, the entire atomic tx reverts — no mint happens, no fee taken. There is no "open Buy NO order" to cancel. This is what makes cancel-on-NO clean without a refund path.

Locked v1 design: NO-side trades are market-only (Option 1)

A "Limit Buy NO" would have to bundle mint_pair (fee taken) + Phoenix limit Sell YES (rests on book). If the limit doesn't fill and the user cancels, they'd be stranded with the unwanted pair, with the 2¢ fee as sunk cost (only recoverable by calling redeem_pair). This violates the "atomic, can't get stranded" promise of POV-3.

Decision: v1 ships Buy NO / Sell NO as market-only. The UI should hide the Limit toggle on NO paths until a v1.5+ decision adds Option 2 (auto-redeem on cancel) or Option 3 (custom matcher with atomic complementary mint).

Where the v1 fee gap lives (DR-009)

Phoenix v1 doesn't expose a per-third-party fee_recipient for markets we don't own. So Phoenix-only secondary trades (Sell YES, Buy NO secondary side, Sell NO secondary side) currently pay $0 protocol fees. The fix is locked in DR-009 amendment 2026-05-24: ~6-8 hr post-submission work to wrap phoenix::InitializeMarket CPI in create_strike_market and set the fee_recipient at market init. Revenue today on devnet = $0, so the gap is theoretical until mainnet + volume.

7. Settlement & redemption

At 4 PM ET on a strike's expiry date, the market settles based on the Pyth oracle close price:

1Cron (Bram's automation) calls settle_market ~4:05 PM ET (after Pyth staleness threshold elapses).
2Anyone can call this — settle is permissionless (DR-002). If cron dies, any user can crank it from the UI.
3Program reads Pyth, validates staleness + confidence, computes outcome: YES if close_price ≥ strike, NO otherwise.
4Program writes strike_market.outcome = Yes | No immutably.
5Users with winning tokens call redeem to claim $1 per token from the vault. Losing tokens are worth $0 (technically still in wallet but no redemption path).

If Pyth fails persistently (15 min of retries with widening confidence): operator can call admin_settle with a manual price, but only after a 1-hour on-chain delay (Hard YES #7).

If the oracle is unrecoverable: market can be settled as Invalid, which triggers redeem_invalid — every user gets their pairs_outstanding position back as USDC (refund of original deposit, no winner/loser).

8. UI honesty check — is the "both books" view wrong?

Diagnosis: mock fixtures are misleading; plumbing is correct

The OrderBookCard in trade-view.tsx has a YES / NO / BOTH view toggle. Today:

  • YES view: hardcoded mock data showing YES book. ✓ correct conceptually (one book, YES side shown).
  • NO view: hardcoded mock data with independent NO prices. ✗ conceptually wrong — there is no separate NO order book; NO prices should be derived as 1 − YES price with sides flipped (a YES ask becomes a NO bid).
  • BOTH view: shows two columns with independent mock prices. Same issue.

The underlying hook (useOrderBook) correctly subscribes to one Phoenix market PDA. The plumbing is right. Only the static mock fixtures lie.

Correct derivation for the NO view

YES book levelDerived NO equivalent
Ask 0.555 × 490Bid 0.445 × 490 (someone selling YES @ $0.555 is willing to "buy NO @ $0.445")
Bid 0.500 × 560Ask 0.500 × 560 (someone buying YES @ $0.500 is willing to "sell NO @ $0.500")

Sides flip because buying YES at price P is the same trade as selling NO at price 1−P. The size (contracts) stays the same.

Recommended fix (v1.5 — UI polish)

When useOrderBook returns live data, the NO and BOTH views should call a derived helper: noBook = { asks: yesBook.bids.map(invert), bids: yesBook.asks.map(invert) } where invert({price, size}) = {price: 1 - price, size}. Single source of truth: the Phoenix YES market.

9. What we have NOT built (and why)

Atomic complementary-mint on fill (Polymarket's CTF Exchange pattern)

Polymarket has a special exchange contract that, when a Buy YES @ $0.60 order meets a Buy NO @ $0.40 order, atomically mints 1 YES + 1 NO from $1 of pooled USDC and gives one to each user. This is "complementary mint on match" — neither user has to mint a pair first.

Phoenix v1 does not support this. Our v1 uses the simpler model: users mint pairs explicitly via mint_pair when they want NO (bundled atomically with the YES sell so it's invisible to the user). The trade-off:

PatternProsCons
Our model: explicit mint_pair + Phoenix bundlingWorks on stock Phoenix v1; no custom matcher; transparent vault math; simple audit.Always uses vault as counterparty for first trade on a strike; no "purely matched" trades possible.
Polymarket CTF modelTwo opposite buyers can match without either having to mint first.Requires custom matching engine; complex audit category; only valuable at high liquidity.

For our use case (binary options on stocks, $1 fixed payout, daily expiry), the explicit-mint model is strictly fine. It's how Polymarket's users behave in practice anyway — most liquidity comes from market makers minting pairs and listing both sides.

Future enhancement: custom matcher with atomic complementary-mint (Polymarket CTF Exchange pattern)

What it would unlock: a "Limit Buy NO" order could meet a "Limit Buy YES" order on the same book and atomically mint a fresh pair to satisfy both — no pre-existing inventory required. This is how Polymarket's CTFExchange + AdapterTrampoline contracts work.

Cost: custom matching engine (forking Phoenix or building from scratch); audit category jumps from "wrapper around audited Phoenix" to "novel matcher" (~$50-200K audit per DR-009). 2-4 weeks senior eng. Loses Phoenix's integrator network (Jupiter routes through Phoenix, not us).

When it becomes ROI-positive: at $1M+ daily volume per DR-009 — fork-Phoenix conversation resumes there. Tracked as Option 4 in specs/clob-strategy.md. v1 explicitly defers per DR-001.

Market maker / automated price seeder

Not built in v1. Without one, every strike requires a human user to seed the first price via either a limit order or a mint+sell pattern. For demo: we either seed manually pre-demo, or we lead with the Buy-YES path which always works against a fresh strike (via mint_pair if the book is empty — though this would actually require posting a limit and waiting, since mint_pair just gives both tokens). The cleanest demo path: use mint_pair directly to bootstrap a strike, then run the full Buy/Sell cycle on a strike that already has depth.

DR-009 Model D — Phoenix fee capture

v1.5 P0 work. Closes the Phoenix-secondary-fee revenue gap. Locked integration plan in DR-009 amendment 2026-05-24. ~6-8 hr cross-lead work post-submission.

Summary verdict

What we built right (per PRD)
  • One Phoenix YES/USDC market per strike — StrikeMarket.phoenix_market is a single Pubkey field
  • NO is the complement, not a separate book — derived as 1 − YES price
  • 4 trade combinations all implemented as 1 signature / 1 tx — POV-3 atomicity enforced
  • Mint-only fee at mint_pair entry — no fee on cancel, no fee on redeem, no need to refund anything
  • Vault math always conserves: vault USDC ≥ pairs_outstanding × $1
  • Cancel is clean — no upfront fees, Phoenix returns collateral on cancel
  • Redeem at settle: winning side gets $1, losing side gets $0
What needs adjustment (small)
  • OrderBookCard mock fixtures in the trade page show NO prices as if they were independent. The fix is a 10-line helper that derives the NO view from the YES book. Pure UI polish — plumbing is correct. v1.5.
  • Bootstrapping — no MM in v1. Manual seeding for the demo, or lead with Buy-YES + mint_pair patterns. Long-term: add an MM bot or rely on user discovery.
What we deliberately deferred
  • Polymarket-style atomic complementary-mint-on-fill — requires custom matcher; v1 uses the simpler explicit-mint model
  • DR-009 Model D Phoenix fee capture — v1.5 P0, 6-8 hr work, gated on $500K+ daily volume not engineering
  • Market maker — v1.5 product decision (auto-seeder bot vs. manual liquidity provision)
