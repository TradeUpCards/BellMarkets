1. Context

What this is

BellMarkets is the team's implementation of the Gauntlet "Meridian" PRD: a non-custodial Solana dApp where users trade YES/NO binary outcome tokens against bUSDC for "Will [STOCK] close above [PRICE] today?" on the MAG7. Settlement is an on-chain Pyth read shortly after 4:00 PM ET. The order book is in-program (per DR-020 — pivoted from Phoenix integration). Daily lifecycle is orchestrated by an off-chain TypeScript service on Trigger.dev.

Why it exists

Gauntlet cohort project — partner-evaluated build demonstrating the full lifecycle (create → mint → trade → settle → redeem) end-to-end on Solana devnet, with defensible architecture and named trade-offs. Hard final: Mon 2026-05-25 7:00 PM ET. Effective build window: ~4 days.

Who uses it

  • Demo users: retail-style traders on Solana devnet during the demo window; Phantom/Backpack/Solflare wallet, no KYC.
  • Evaluators: Gauntlet reviewers running the lifecycle from the repo + reviewing on-chain via Solscan.
  • Team: validating on-chain invariants and the cron-failure recovery path during dev.

Out of scope (deliberate)

  • No mainnet, no real funds (PRD hard rule)
  • No KYC, no custody, no off-ramp
  • No mobile / no i18n / no multi-tenant
  • Off-chain database is product surface, not protocol authority. Solana is canonical for funds (DR-003 amended); a Neon Postgres serves users, OAuth, AI briefings, notification prefs, leaderboard reads.
  • No fallback CLOB if the in-program matcher has a bug — admin pause is the safety valve

  • No automated rent recovery for OrderBook + escrows post-settle in v1 — deferred to v1.1 as pre-mainnet precondition

2. Spiky Points of View

Disagreeing with one means redesigning the project, not patching it. Each POV has a Decision Record.

POV 1 — Build the matching engine in-program

We run a price-time-priority CLOB inside the Anchor program. place_order is the entry point; the matcher crosses on placement (three-phase plan/settle/apply) and rests the remainder if any. cancel_order is owner-only. match_orders is a permissionless crank. Adopted Keith Mazanec's parallel-cohort reference design with adversarial review pre-applied.

Trade-off: One novel audit surface (gated for mainnet on a formal third-party audit), in exchange for: no Phoenix devnet bootstrap dependency, smaller audit surface concentrated in one program, escrow telescoping without dust, stronger "we built it" interview narrative. DR-020 supersedes DR-001.

POV 2 — On-chain owns the rules; off-chain owns the schedule

settle_market is callable by anyone. The Anchor program enforces all timing rules + Pyth staleness + Pyth confidence + the time-delayed admin override. Automation is a convenience caller — first to crank wins — not an authority. Admin override (admin_settle) is on-chain time-delayed (≥1hr) and used only when Pyth fails.

Trade-off: ~half a day of extra on-chain timing-logic work + benign race-condition wasted fees, in exchange for cheaper mainnet ops (~5–10×), better scaling (load distributes to user demand), stronger demo defense ("our cron can die and the system still works"), engineering symmetry with the in-program matcher's permissionless-crank philosophy. DR-002

POV 3 — Buy NO is a first-class atomic operation; UI never exposes mint-and-sell

Four buttons: Buy YES, Buy NO, Sell YES, Sell NO. Each = one wallet-signed transaction. Buy NO bundles mint_pair + place_order(SELL_YES, IOC) atomically (user keeps the NO, effective cost = $1 − YES_sale_price); Sell NO is the inverse. Users never see a "mint pair" button, never see a YES token they don't want.

Trade-off: More frontend complexity (bundled atomic transactions, position-aware button states, four-button mental model) in exchange for UX that matches user intent rather than protocol internals. DR-019 amendment: Limit-side NO trades are disabled (NO is market-only) because a resting Limit NO would strand fees on cancel.

4. Guardrails

Hard NOs enforced

  1. 1.Never use mainnet or real funds for the core submission (PRD).
  2. 2.Never commit secrets / private keys / mnemonics / API keys / RPC keys to git. .env only; keys/ directory gitignored.
  3. 3.Never use npm install or yarn add — pnpm always. Delete any package-lock.json / yarn.lock that sneaks in.
  4. 4.The matcher is in-program now (DR-020). Reject PRs that try to swap it for Phoenix or another CLOB without a new DR superseding DR-020.
  5. 5.Never give settle_market a special-signer requirement (DR-002).
  6. 6.Never add a fallback oracle (DR-003). Pyth or admin override only.
  7. 7.Never leak the mint-and-sell mechanic to the trade UI (POV-3). Buy NO / Sell NO are atomic single-tx operations from the user's perspective.
  8. 8.Never violate the $1 USDC invariant — yes_payout + no_payout = $1.00 exactly. Fees route through fee_collector, never out of usdc_vault.
  9. 9.Never commit files under .project/ or .claude/ — OneDrive-mirrored, gitignored by construction.
  10. 10.Never git push --force to main without explicit user request.
  11. 11.Never dump raw oracle / RPC / wallet logs (>20 lines) into handoffs, session recaps, or commit messages.
  12. 12.Never use live stock prices in unit / integration tests — synthetic / mocked Pyth feeds only.
  13. 13.The Helius API key NEVER appears in NEXT_PUBLIC_*. Server-side proxy only. A leaked key is a leaked credential, full stop.

Hard YESes enforced

  1. 1.The $1 USDC invariant is verified on-chain. mint_pair debits exact amount + mints exact amount of YES + NO; redeem_pair is the inverse; redeem post-settle pays $1 to the winning side; vault holds exactly pairs_outstanding × $1. Drew's invariant test suite + Aria's Rust property tests cover this.
  2. 2.The full lifecycle is demoable end-to-end on devnet. Create → mint → trade → settle → redeem. Verified 2026-05-25.
  3. 3.pnpm always — every script / CI / README / package.json references pnpm. Permanent user preference.
  4. 4.Every PR runs: anchor test + pnpm test + pnpm typecheck + pnpm lint. CI fails the merge if any fail.
  5. 5.The demo includes the cron-failure path — settle from a non-cron wallet. Load-bearing evidence for DR-002.
  6. 6.settle_market validates Pyth staleness AND confidence; both thresholds configurable; outcome immutable once written.
  7. 7.admin_settle has an on-chain time-delay gate (≥1hr after settlement window).
  8. 8.Position-exclusivity is a frontend guardrail — UI prevents Buy YES while holding NO (and vice versa). Benign if bypassed (user redeems pair for $1).
  9. 9.Order book + portfolio views update via WebSocket (onAccountChange). Reconnect-on-disconnect handled.
  10. 10.Frontend uses @solana/wallet-adapter-react for all signing — no in-app keystore, no env-var private keys for "test flows."
  11. 11.Every Spiky POV has a Decision Record in constitution/decisions.md with the trade-off line spelled out.
  12. 12.All matcher CPI transfers are PDA-signed with strike_market as authority — never the user. Maker payout ATAs validated for ownership + mint before the CPI fires.

Things to flag for human review (not auto-block)

  • Adding any new dependency beyond the locked stack — name a one-line "why" first.
  • Touching the vault PDA seeds, OrderBook schema, or StrikeMarket account schema after deploy_index=9.
  • Any change to place_order, cancel_order, match_orders, settle_market, mint_pair, or redeem — pause for property-test coverage review.
  • Any cross-workstream PR (e.g., programs/ + apps/web/) — both owning leads must sign off.
  • Any deviation from a Spiky POV — write a new DR before implementing.
